# Compositional Navigation Memory (CNM)

Compositional Navigation Memory is a deployment-time adaptation framework for
robot navigation. A robot does not adapt by updating its policy after every new
encounter. Instead, it retains verified closed-loop executions as structured
experience, connects compatible experience through explicit physical
interfaces, and revises the evidence attached to that experience when it is
executed again.

The implementation follows one continuous loop:

```text
local execution
    -> immutable execution event
    -> verified entry-response-exit record
    -> uncertainty-aware memory graph
    -> closed-loop composition
    -> new task capability
    -> new execution evidence
    -> reliability revision
```

This repository contains the algorithm modules and registered experiment
runners used for embodied experience formation, individual capability growth,
collective capability from complementary histories, and the comparisons shown
in `Fig02_EEF_Training_Efficiency_v6` and `Fig05_CNM_Comparison_v2`.

## Core idea: experience is the adaptive state

CNM separates the system into two states.

### Frozen execution stack `W*`

The following components are fixed after training:

- the embodied execution policy and its encoder;
- the local command vocabulary and response horizon;
- terminal-outcome calibration;
- record-admission thresholds;
- retrieval, placement, connection and search rules;
- evidence kernels, reliability thresholds and memory operators.

`algorithm/frozen.py` serializes these elements, their configurations and
operator-source hashes into a `FrozenStackManifest`. Every experiment stores
the resulting `frozen_stack_sha256` so that a memory generated by one execution
stack cannot silently be evaluated with another.

### Adaptive experience state `A(i,t)`

For robot `i`, deployment-time adaptation is represented by:

```text
A(i,t) = {verified experience records, unique execution events}
```

An `ExperienceRecord` stores:

- structural key and behavioral role;
- context;
- finite entry support and entry uncertainty;
- closed-loop response command;
- finite exit support and exit uncertainty;
- source-linked execution evidence;
- origin, executor and parent-record provenance.

The graph used for a query is reconstructed from the current records and
evidence. It is not an independently trained network. Consequently, capability
can change while the policy and all memory operators remain unchanged.

## How CNM works

### 1. Embodied experience formation

`algorithm/eef.py` implements the execution policy and its training signals.
The trainer combines:

1. **Privileged feasibility guidance** to reject responses that violate
   progress, clearance or actuation constraints during training.
2. **Differentiable physical rollout** to expose delay, drag and realized
   terminal motion to the learning objective.
3. **Terminal-outcome supervision** to predict a seven-dimensional terminal
   distribution over position, velocity and heading.

The policy therefore produces a local response and an estimated distribution
of its physical exit. These predictions are later checked against measured
executions; prediction alone never creates a verified record.

### 2. Execution events and record verification

Every attempted response is converted to an immutable `ExecutionEvent` before
the admission decision. Its deterministic identifier and content hash make
event-ledger union idempotent: forwarding the same event twice cannot increase
confidence twice.

`algorithm/experience.py` converts repeated `FlightSegment` objects into
verified records. Admission checks completion, clearance, command support,
absolute terminal residual, covariance-normalized terminal residual and the
minimum number of independent successful executions. Finite entry and exit
samples are retained alongside robust means and covariances. BIC-supported
multimodal exits are split into separate record variants instead of being
averaged into a broad, misleading interface.

### 3. Individual composition

`CNMPlanner` in `algorithm/memory.py` performs retrieval, placement and graph
construction. An edge is admitted only when:

- the predecessor exit and successor entry overlap in finite support;
- their uncertainty-normalized distance passes the connector gate;
- the local bridge is observed free and remains within its duration and
  acceleration limits;
- the command remains inside the frozen command domain;
- the conservative chain reliability remains above its threshold.

Bounded A* search ranks supported chains by duration, reliability, terminal
uncertainty, evidence age, congestion and interface mismatch. Only the first
response of a selected chain is executed. `algorithm/rollout.py` then replans
from the measured exit, so a nominal chain is never replayed open loop.

### 4. Collective circulation and execution return

Each robot owns a private `CNMLibrary`. When a role or connector is missing,
`select_for_query` ranks transferable experience by query relevance, identifier
novelty, verified utility, source diversity, byte cost and evidence age.

Transferred records preserve provenance. After a recipient executes a
transferred response, the new source-linked event is merged through the same
evidence update used for private experience. Later recipient success can
reinforce the response; a matched failure can reduce its context-specific
reliability. This is how complementary histories become collective capability
without replacing private memory by a single global model.

## Installation

Python 3.10--3.12 is supported. From the directory containing `code_source`:

```powershell
cd code_source
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[train,test]"
```

On Linux or macOS, activate the environment with:

```bash
source .venv/bin/activate
```

Verify the installation:

```powershell
python -m pytest
python -m cnm_swarm_sim.validate_release
```

The first command checks event formation, record compilation, composition,
deletion/restoration, transfer idempotence, evidence revision and the explicit
unseen `A+C+B` task. The second command checks the frozen manifest, registered
task set and bounded planner configuration.

## Running individual CNM growth

The individual experiment crosses the trained policies with independent
acquisition seeds and evaluates 24 read-only held-out tasks. The registered set
contains new ordering, placement and interface-shift tasks, including the
explicit `A+C+B` composition.

```powershell
python -m cnm_swarm_sim.run_reconfigurable_individual_cnm `
  --eef-run runs/eef_training_efficiency_v5 `
  --output runs/individual_cnm_reconfigurable_v2 `
  --acquisition-attempts 5 `
  --resume
```

The runner records every acquisition attempt, compiler decision, selected
chain and replan boundary. Probes use read-only memory snapshots. It also
executes four causal branches:

1. full adaptive state;
2. deletion of records used by the successful composition;
3. deletion of matched irrelevant records;
4. exact restoration of the original state.

The adaptive-state digest and frozen-stack hash are stored for every branch.

## Running collective CNM

```powershell
python -m cnm_swarm_sim.run_collective_cnm_experiment `
  --eef-run runs/eef_training_efficiency_v5 `
  --output runs/collective_cnm_v5
```

The collective protocol evaluates 2-, 4- and 6-robot teams on three registered
reconfigurable tasks. Each private history lacks at least one required
experience, while the union contains a supported composition. The conditions
include:

- private CNM;
- replication of the best individual history;
- redundant histories;
- one-time pooling;
- unrestricted exchange;
- selective CNM circulation;
- source withholding;
- feedback withholding.

The runner writes:

- `collective_trials.csv`: whole-team completion and selected chains;
- `complementarity_audit.csv`: private versus union support;
- `transfer_audit.csv`: records, events, recipients and communicated bytes;
- `execution_return_events.csv`: recipient-measured source-linked evidence;
- `adverse_return_probes.csv`: reliability change after controlled failures;
- `frozen_stack_manifests.json`: the fixed stack used by every team.

## Reading and auditing a run

The most useful audit fields are:

- `frozen_stack_sha256`: proves which fixed policy and operators produced the
  run;
- `event_id` and `content_hash`: prevent duplicate evidence;
- `origin_robot` and `executor_robot`: retain transfer provenance;
- `selected_chain` and `selected_chain_reliability`: expose the planner choice;
- `edge_audit`: records accepted and rejected connector tests;
- `replan_events`: identify the measured exit used by the next query;
- `operator_audit`: records merge, deletion, restoration, transfer and
  withholding operations;
- `adaptive_state_digest`: verifies read-only probes and exact restoration.

All experiment tables are ordinary CSV or JSON files so that reported metrics
can be recomputed without loading the simulator.

## Determinism and extension points

Seeds, registered tasks, thresholds and source hashes are written to each run
manifest. Event identifiers are deterministic for identical event content, and
packet merging is commutative and idempotent.

New environments or robot platforms can be integrated while preserving the CNM
logic by implementing the same boundary objects:

1. produce a measured `FlightSegment` for every attempted local response;
2. provide terminal predictions and calibration metadata;
3. preserve the seven-dimensional entry/exit state convention;
4. keep frozen-stack and event provenance in serialized outputs;
5. execute one selected response before replanning from the measured exit.

Following these interfaces keeps changes attributable to experience formation,
record verification, composition, evidence revision or circulation rather than
mixing them with untracked policy updates.
